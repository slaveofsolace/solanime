# Solanime protected-player prototype

This is an **isolated native experiment**, not a released mobile app or proof that every provider plays safely. It loads Solanime in an app-owned WebView without a native JavaScript bridge. Android source is a minimal Gradle project. The iOS Xcode project and shared scheme compile, and a locally signed `Solanime 0.1.0 (9)` Release-configuration build is installed and launched on an iPhone 16 Pro. The owner reported seeing playback on an earlier build; five-second video progress, changed frames, and zero unwanted windows have not yet been measured together on build 9. The native release gate remains open.

## Why this exists

Brave's public [Shields architecture](https://github.com/brave/brave-core) filters requests inside the browser, backed in part by [adblock-rust](https://github.com/brave/adblock-rust). A Solanime webpage cannot acquire those browser privileges over a foreign player iframe. This prototype starts with the smaller browser-host capability the popup failure needs: reject new windows **outside** the page's JavaScript, and independently cancel disallowed document navigation. No Brave code or filter list has been copied. The first-party policy code is based on the Android and WebKit platform APIs.

Android enables multiple-window request handling and refuses every `onCreateWindow` call, including a user-initiated one. Simply disabling multiple windows is unsafe: Android may turn `window.open` into navigation of the current WebView. Main-frame navigation is restricted to `solanime.pages.dev`; subframe documents are initially restricted to that host, `megaplay.buzz`, and `www.youtube-nocookie.com`. External app launches are not forwarded. iOS uses `WKUIDelegate` and `WKNavigationDelegate` for the analogous decisions, including a response URL check after redirects. Both intentionally keep the HTML iframe unsandboxed during the compatibility experiment.

As a separate, narrower layer, Android request interception and an iOS WebKit content rule block the exact ad hostname `wuytg.com` observed in the dated Android click trace. The iOS rule also blocks popup resource loads, and the UI delegate independently refuses new WebViews. The iOS app fails closed with a retry state if its content rules do not compile. This is **not** a complete ad list and must not be confused with the browser-host window policy. Android's request callback does not cover every redirected resource URL.

## Build and acceptance state

On a machine with JDK 17+, Android SDK 36, Android Gradle Plugin-compatible Gradle, and an attached Android device, open `mobile-prototype/android` in Android Studio and run the debug app. No Android runtime result is claimed here. To test iOS, open `ios/SolanimeProtectedPlayer.xcodeproj` in Xcode on a Mac, select your development team locally, and run the shared `SolanimeProtectedPlayer` scheme on a physical iPhone. Keep signing identities and profiles outside Git. Debug builds use the exact `https://cloud-release.solanime.pages.dev/` first-party preview origin so the installed phone can review current UI; Release builds use `https://solanime.pages.dev/`. Both retain the same popup and document-navigation protections. The exact commands, installed build, acceptance evidence, and remaining release gate are in `NATIVE_PLAYER_MAC_HANDOFF_20260929.md`.

The first test target is mapping `384944`, which previously advanced visible video in emulated Android Chromium while opening one unrelated popup in an ordinary browser. Test new-window requests, `target=_blank`, delayed and click-triggered popups, `_top` navigation, GET/POST redirects, external schemes, fullscreen, seeking, episode switching, and account login. Log *attempts*, actual windows, committed top-level URLs, external launches, video time, and presented frames. A failed popup attempt with video still playing is a promising prototype result; neither window rejection alone nor iframe load establishes playback. Check a physical Android phone and iPhone separately. If either provider refuses this host or navigation escapes before cancellation, do not weaken protection and do not release the app.

This prototype does not implement Brave's full request filter engine, cosmetic filtering, or filter-list updates. Those are later, separate decisions: first establish whether native window/navigation containment preserves video. Provider ads rendered **inside** the existing frame can remain, and third-party playback permissions/distribution are separate release gates. The ordinary website/PWA does not inherit these native protections.

## Source disposition

| Candidate | License observed | Decision for this prototype |
| --- | --- | --- |
| [Brave Core](https://github.com/brave/brave-core) | MPL-2.0 | Reference architecture only; Chromium-specific integration is not imported. |
| [adblock-rust](https://github.com/brave/adblock-rust) | MPL-2.0 | Hold as a later network-filter candidate; not imported or needed to reject windows. |
| [Capacitor](https://github.com/ionic-team/capacitor) | MIT | Viable later React/native shell; not needed for this isolated WebView experiment, so no dependency added. |

The candidate registry files in `docs/*-mobile-candidate.json` record discovery separately from import or release. A shallow `adblock-rust` checkout at `1c0740d27d531a2389c808212a8702592bb74138` was inspected solely for its license and API surface. Its README documents request filtering and Apple content-rule conversion, but that checkout contains no ready Android JNI or iOS Swift binding. Nothing from it has been copied into, built for, or shipped with Solanime; the candidate remains on hold.

The first Android and iPhone device runs must also check account sign-in, the prior iPhone `102630` media error, and whether third-party cookies are required for playback. If any of those fail, record the exact platform and mapping; do not silently turn off the window policy or accept an external popout as a fix.

On a Mac, `swift mobile-prototype/ios/validate-content-rules.swift` submits the exact rule JSON embedded in the iPhone source to WebKit's content-rule compiler. This caught and fixed an unsupported regular-expression disjunction on 2026-09-29. A successful rule compilation is only a source preflight; it does not compile the iOS app or prove playback. Debug builds opt the WebView into Safari Web Inspector on iOS 16.4 and later so the physical-device run can inspect video time, frame data when available, and the `102630` failure without adding a JavaScript bridge. Release builds leave inspection disabled.
